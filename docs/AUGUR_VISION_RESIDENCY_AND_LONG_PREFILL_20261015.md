# Vision 优先常驻与长 prefill 显存验收

日期：2026-10-15。**产品默认保持 `on_demand`**（按需加载、编码后释放 GPU 权重）；本报告验证的 `auto` 常驻回收方案仅供显式选择，不自动启用。两种模式都保留已转换的 CPU 权重。

## 结论

- 仅在显式选择 `auto` 时，启动预热后的视觉编码器保留在 GPU，跟 target 和 Q8_0＋FP32 gate0.45 DFlash 权重共同驻留。默认 `on_demand` 仍在编码后释放 GPU 编码器。
- 编码器显式分配 **928111554 bytes，约 885.12 MiB**。驱动总显存变化还包括 CUDA 内部开销，不与该数值混淆。
- 在分配 B4352 prefill 工作区之前，按实际可用显存检查预算；不足则先回收 Vision。若仍不足，现有调度继续释放可重建的 B8 验证计划；不降低 KV 容量、批宽或精度。
- 回收后保持 CPU 权重，下一次图片请求重新上传，随后连续图片再次命中常驻编码器。不在文本请求结束后抢占显存主动重新加载 Vision。
- 8K／32K／64K 全量无缓存 prefill 均成功，无 OOM。17 项配对请求的完整输出 token ID 一致。此处包含截断为 32 个输出 token 的长代码性能探针，不表示长代码完整性验收。

## 显存压力账单

测试使用 32 GiB Tesla PG503-216，完整预分配 **262144-token 物理 KV**，固定 B8、B4352、原始 target 权重、Q8_0＋内置 FP32 gate0.45；图片生成维持原生 target 保护。

无已缓存 B8 验证计划时，Vision 常驻后的空闲约 **994 MiB**；prefill 预算需要约 **1617 MiB**（包含原有 128 MiB 安全预算）。回收 Vision 后可用约 **1888 MiB**，prefill 显式工作区约 **1472.06 MiB**。因此不回收的永久常驻会过不了这一预算检查。

加严条件：每次长 prefill 前先做真实短 Python 代码生成并执行测试，让 **Vision 和 B8 验证计划都已驻留**。随后只回收 Vision，B8 计划可继续保留并恢复。该条件下采样峰值已用 **32494 MiB**，最低可用 **133 MiB**；按需加载的同条件对照也为 133 MiB。

**余量很紧，不能承诺同时运行其他 GPU 程序也不会 OOM。** 预算判断读取当时实际 `cuda_memory_info`；采样间隔约 0.2 秒加 `nvidia-smi` 调用开销，采样峰值不是精确瞬时峰值。

已测试的实际输入最长 65520 token，而不是一次实际 256K-token prefill。完整 KV 分配不能替代实际 256K 输入验收。

## OCR 收益与恢复

在配对的 **6 次常驻命中**中，同一低分辨率合成图片 `426` 使用两种问题表述，全部正确：

| 指标 | 按需加载 | 常驻命中 | 减少 |
|---|---:|---:|---:|
| 视觉阶段，含必要上传与释放 | 97.11 ms | 23.52 ms | 73.59 ms |
| 完整 HTTP EOF 墙钟 | 669.47 ms | 596.52 ms | 72.94 ms |

这组收益不包括刚被回收后必须重新上传的图片请求，也不是对任意图片尺寸或 OCR 数据集的保证。长 prefill 后的图片恢复、连续图片复用、3 组短代码执行、图片流中途断开后的同 owner 图片／文本恢复均通过。4 轮完整 GPU 验证全部正常退出，原生分配账单回到零。

## 配置与监控

- 默认：`--vision-residency on_demand`。显式可选方案：`--vision-residency auto`。
- 原生 owner 同名环境配置为 `AUGUR_VISION_RESIDENCY`；产品启动器清理旧实验环境后按 CLI 选项设置，避免遗留环境偷偷改变默认值。
- 每轮原生回执记录 `vision_residency`（常驻字节、上传次数、命中、回收原因），prefill 回执记录 `vision_memory_budget`。
- 监控显示最近完成请求的 Vision GPU／CPU 状态，明确不冒充请求运行过程的瞬时状态。
- 可用显存改为读取 `nvidia-smi memory.free`，不以 `memory.total - memory.used` 替代；本机存在约 142 MiB 驱动保留显存，后者会高估余量。
